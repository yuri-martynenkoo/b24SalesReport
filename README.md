# Аналитика продаж для Битрикс24

Встраиваемый VibeCode-дашборд по сделкам CRM. Приложение работает через Black Hole Gateway от лица сотрудника, который открыл пункт меню в Битрикс24.

- Приложение: https://app-916c4e0a9320.vibecode.bitrix24.tech
- Исходный код: https://github.com/yuri-martynenkoo/b24SalesReport
- Краткие [материалы для проверки](SUBMISSION.md)


## Возможности

- количество и сумма сделок по каждой стадии (`stageId`) в таблицах, сгруппированных по направлению;
- отдельные показатели суммы и количества открытых и выигранных сделок, средний чек выигранных;
- 15 последних по дате создания сделок со ссылками на карточки, направлением, стадией, ФИО ответственного и его подразделением; сортировка столбцов меняет порядок только этих 15 сделок;
- фильтры по направлению, ответственному и дате создания: 7/30/90 дней, текущий квартал или произвольный диапазон; быстрый период применяется по нажатию, остальные фильтры — после подтверждения выбора, без кнопки «Применить»;
- сводка по стадиям, KPI и список ответственных строятся через `POST /v1/deals/aggregate`; только последние 15 сделок читаются через `GET /v1/deals?limit=15&sort=-createdAt`;
- если агрегация сообщает об усечении или отвечает `422 AGGREGATION_LIMIT_EXCEEDED`, период делится на меньшие интервалы; неполные суммы не показываются;
- корректные итоги для нескольких валют;
- responsive-интерфейс с компактными KPI-карточками и лёгкой фоновой заливкой, состояния загрузки, ошибки и пустой выбор.

Все показатели, стадии и последние сделки относятся к **одному выбранному периоду создания** и направлению. Список ответственных строится по доступным сделкам выбранного направления и периода; по умолчанию выбран вариант «Все ответственные», то есть дополнительного ограничения нет. При смене направления выбор ответственного сбрасывается. «Выигранные за период» — это сделки, созданные в период и находящиеся в выигранной стадии сейчас; это не показатель по дате закрытия. Открытые сделки, созданные до начала периода, также не входят в KPI. Суммы группируются по направлению и `stageId`; суммы разных валют показываются отдельно.

Кнопка «Текущий квартал» выбирает даты с первого дня текущего календарного квартала по сегодняшний день. Это не последние 90 дней: в начале квартала такой диапазон может быть короче, чем «30 дней», и показывать меньше сделок.

## Безопасность и авторизация

Ключ `vibe_app_…` хранится только в секрете/переменной окружения `vibe_app_local` (также поддерживается alias `VIBE_APP_KEY`). Значение не попадает в HTML, JavaScript браузера или Git; `.env` исключён из репозитория. Gateway передаёт серверу `X-Vibe-Authorization`, а сервер обращается к VibeCode с ключом приложения в `X-Api-Key` и сессией текущего пользователя в `Authorization: Bearer`. Доступны только те сделки, которые сотрудник вправе читать в Битрикс24.

Для рабочего сервера выбрана политика доступа `PORTAL`: дашборд предназначен всем авторизованным сотрудникам своего портала с соответствующими правами CRM, а не только владельцу сервера (`OWNER_ONLY`). Политика `PUBLIC` неприемлема для отчёта по реальным сделкам. Проверка анонимного `GET /api/dashboard` через действующий шлюз 20.10.2026 вернула `401 BH_LOGIN_REQUIRED`; это проверка шлюза, а не локальной проверки `AUTH_REQUIRED` в Node.js.

Для решения нужны следующие скоупы:

| Скоуп | Назначение |
| --- | --- |
| `crm` | Чтение сделок, направлений и стадий. |
| `user` | ФИО ответственных из `/v1/users`; `user_basic` для этого маршрута недостаточен. |
| `department` | Названия подразделений ответственных. |
| `placement` | Публикация и открытие приложения внутри Битрикс24. Дополнительный `LEFT_MENU` в действующей установке не создаётся. |
| `vibe:infra` | Деплой на Black Hole server и резервный поиск ФИО через справочник сервера, если `user` недоступен. |

Текущий выданный ключ содержит также дополнительные скоупы платформы, которые код отчёта не использует; их можно сократить при плановой перевыпуске ключа и повторной авторизации. См. документацию VibeCode: [сделки](https://vibecode.bitrix24.tech/docs/entities/deals/list), [сотрудники](https://vibecode.bitrix24.tech/docs/entities/users), [отделы](https://vibecode.bitrix24.tech/docs/entities/departments/list), [места встраивания](https://vibecode.bitrix24.tech/docs/apps/placements), [инфраструктура](https://vibecode.bitrix24.tech/docs/infra).

## Известные ограничения

- Границы выбранных дат передаются в API как `00:00:00Z`—`23:59:59.999Z` (UTC), а не в часовом поясе портала.
- Агрегация VibeCode обрабатывает максимум 5 000 сделок за вызов. Код делит выбранный период по датам при `data.meta.truncated`, усечении групп или `422 AGGREGATION_LIMIT_EXCEEDED`, затем объединяет полные результаты. Если за один день лимит всё ещё превышен, отчёт показывает явную ошибку вместо неполных KPI. Тест разбиения 5 201 сделки выполнен на имитации API, не на реальном портале.
- Для раздельных сумм по валютам выполняется агрегация по каждой валюте из справочника портала; итоговое количество сверяется с общим счётчиком. При неполном справочнике или несовпадении отчёт не показывается.
- Списки сотрудников и отделов запрашиваются максимум по 5 000 записей каждый; в очень большой организации ФИО или подразделение отдельных ответственных могут быть недоступны.
- Без портальной сессии политика `PORTAL` возвращает `401 BH_LOGIN_REQUIRED` на самом шлюзе, в том числе для `/api/dashboard`; такой ответ не свидетельствует об ошибке Node.js. Успех `/health` под авторизованным пользователем подтверждает запуск сервиса, но не доступ этого сотрудника к CRM.

## Локальная проверка

Требуется Node.js 20 или новее, внешних npm-зависимостей нет.

```bash
npm run check
```

Команда проверяет синтаксис и запускает тесты, включая разбиение усечённой агрегации 5 201 сделки, обработку `422`, запрос 15 последних сделок, `404` на ошибочных статических путях, ссылку на карточку и группировку стадий. Для реальных данных приложение должно быть открыто из Битрикс24: локальный браузер не получает защищённый заголовок Gateway.

## Развёртывание VibeCode

Ниже — порядок **нового развёртывания на своём портале**, а не команда обновления действующей установки автора. Нужны доступ к VibeCode на этом портале, право создавать приложения и серверы, ключ с `vibe:infra` и доступом именно к выбранному серверу, а также Git/PowerShell для примера ниже. Это может быть личный `vibe_api_…` или связанный с сервером `vibe_app_…`; все управляющие запросы идут с ним в `X-Api-Key`. Тарифы и доступные конфигурации сервера зависят от портала. Проверяющему без собственного портала достаточно изучить код и выполнить `npm run check`; живые данные CRM без авторизации пользователя недоступны.

1. **Создайте свой сервер Black Hole.** В кабинете VibeCode выберите отдельный сервер (`STANDALONE`, не Galaxy), доступные провайдер и план. Эквивалентный API-маршрут — [`POST /v1/infra/servers`](https://vibecode.bitrix24.tech/docs/infra/servers/create), с полями `name`, `provider`, `plan` и `placement: "dedicated"`. Дождитесь `status: running` и `blackholeStatus: CONNECTED` через `GET /v1/infra/servers/:id`. Запишите **свой** UUID сервера и URL вида `https://app-….vibecode.bitrix24.tech`; UUID из исходного кода относится к установке автора.
2. **Создайте OAuth-приложение** на том же портале: [`POST /v1/apps`](https://vibecode.bitrix24.tech/docs/apps/create) с названием, `appUrl` вашего сервера и скоупами `crm`, `user`, `department`, `placement`. Проверьте по `GET /v1/me` права парного ключа; для резервного серверного поиска сотрудников нужен также `vibe:infra`. Сохраните одноразово выданный ключ `vibe_app_…` вне репозитория. В разделе `/applications` найдите карточку, которая показывает **именно ваш сервер** (сверьте его ID), и в ней создайте секрет `vibe_app_local` со значением ключа: платформа передаёт [секреты карточки приложения](https://vibecode.bitrix24.tech/docs/applications/app-secrets) в процесс связанного сервера. Если карточка показывает другой сервер или сервер не связан, остановитесь и исправьте привязку до деплоя. Значения секретов через API не передаются. `VIBE_APP_KEY` в коде — лишь локальный alias: имена `VIBE_*` как секреты платформа не принимает. Если раздел секретов на портале недоступен, настройте защищённую переменную окружения службы отдельно, не помещая ключ в архив, Git или пример команды деплоя.
3. **Подготовьте архив исходников из своего checkout и разверните его.** Из корня репозитория выполните `npm run check`, затем команды PowerShell ниже. Для платформы это [`POST /v1/infra/servers/:id/deploy`](https://vibecode.bitrix24.tech/docs/infra/deploy/deploy): обязательны `source` и `start`; при включённом хранилище `source.content` сохраняет снимок исходников для последующей публикации. Выбранный ключ идёт **только** в `X-Api-Key`. Перед деплоем проверьте, что `GET /v1/infra/servers/:id` с этим ключом возвращает нужный сервер; ключ от другого владельца может видеть тот же портал, но не этот сервер. Не подставляйте ID сервера автора.

   ```powershell
   $projectServerId = '<UUID вашего сервера>'
   $projectApiKey = [pscredential]::new('key', (Read-Host 'Ключ VibeCode с доступом к серверу' -AsSecureString)).GetNetworkCredential().Password
   $projectArchive = Join-Path ([IO.Path]::GetTempPath()) 'b24-sales-report.tar.gz'
   git archive --format=tar.gz --output=$projectArchive HEAD
   $projectBody = @{
     source = @{ content = [Convert]::ToBase64String([IO.File]::ReadAllBytes($projectArchive)) }
     runtime = 'node20'
     start = 'cd /opt/app && node src/server.js'
     port = 3000
     healthPath = '/health'
     serviceName = 'sales-report'
     env = @{ VIBE_SERVER_ID = $projectServerId }
   } | ConvertTo-Json -Depth 6
   $projectDeploy = Invoke-RestMethod -Method Post `
     -Uri "https://vibecode.bitrix24.tech/v1/infra/servers/$projectServerId/deploy" `
     -Headers @{ 'X-Api-Key' = $projectApiKey } `
     -ContentType 'application/json' -Body $projectBody -TimeoutSec 600
   if (-not $projectDeploy.success) { throw "Деплой не завершён: $($projectDeploy.error.code)" }
   $projectDeploy.data.appUrl
   ```

   Этот пример относится к **первой выкладке на отдельный сервер**. Для Galaxy часть полей (`serviceName`, `preserveEnv`, `hardening`) не действует, а порядок создания отличается — используйте [инструкцию платформы](https://vibecode.bitrix24.tech/docs/infra/servers/create). При повторной выкладке не меняйте `serviceName`; если используете собственный `.env` на отдельном сервере, сохраняйте его явно (`preserveEnv: true`). Секрет карточки приложения доставляется отдельно от `.env`. Код читает `VIBE_SERVER_ID` для резервного поиска ответственных: на чужом сервере его необходимо заменить.
4. **Авторизуйте и опубликуйте приложение.** Если при публикации платформа сообщает `NO_USER_TOKEN`, пройдите [OAuth-авторизацию приложения](https://vibecode.bitrix24.tech/docs/keys-auth/oauth) на своём портале. Затем вызовите [`POST /v1/apps/:id/publish`](https://vibecode.bitrix24.tech/docs/apps/publish) с `appUrl` своего сервера и `placements: []`: отдельный `LEFT_MENU` создаёт второй одноимённый пункт. Если хранилище исходников включено и снимок деплоя принадлежит серверу, укажите `sourceServerId` этого сервера; при `SNAPSHOT_REQUIRED` следуйте `hint` ответа. Публикация и деплой — разные операции. Управляющие запросы отправляйте с ключом в `X-Api-Key`; `Authorization: Bearer` нужен только там, где документация требует пользовательскую OAuth-сессию.
5. **Настройте доступ `PORTAL` и проверьте результат.** Установите для сервера `accessPolicy: PORTAL`, чтобы приложение открывалось сотрудникам этого портала, но не анонимным посетителям. У деплоя должен быть `success: true`. Анонимный `GET <appUrl>/api/dashboard` должен вернуть `401` с кодом `BH_LOGIN_REQUIRED` от шлюза. Откройте приложение **из Битрикс24** под сотрудником с правом чтения CRM: убедитесь, что данные загрузились, затем проверьте фильтры, KPI, стадии, сортировку и ссылку на карточку сделки. Проверка `/health` без сессии при `PORTAL` тоже может вернуть `401`; проверяйте её в авторизованном контексте.
